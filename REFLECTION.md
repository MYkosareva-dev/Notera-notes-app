# REFLECTION

## 1. The persistent-storage consultation

The assignment fixed the database — Supabase Postgres, with
`localStorage`/`sessionStorage` ruled out — so before any code existed I asked
Claude Code a narrower question: not *which store*, but *which access pattern*,
given that the signed-in check must be verifiable on the server. It compared
(a) direct access from Server Components and Server Actions, (b) Supabase
behind my own `/api` route handlers — my previous project's shape — and (c) a
browser client with RLS only. Trade-offs surfaced: (a) makes every Server
Action a publicly callable POST, so auth becomes per-function discipline;
(b) adds a second auth idiom and invites the service-role-key trap; (c) turns
the gate into a client-side redirect — the flaw this sprint's scan hunts. It recommended (a), with three
specifics I adopted: RLS as the real boundary, one `server-only` data-access
module that calls `getUser()` itself, middleware demoted to cookie refresh. The argument that settled it: the HTTP seam in my previous project
had *paid out* — this sprint built the database-backed app that seam was
insurance for — and the seam worth keeping now is a module boundary a browser
cannot call. Full record:
`docs/persistence-decision.md`.

## 2. An authentication issue I caught and fixed

Our build plan carried a probe the checklist can't replace: JWT expiry set to
60 seconds, sign in, wait, reload — every standard check fits inside the
default hour, so a broken refresh would still pass. I expected a silent
refresh; instead the reload bounced me to `/sign-in`. Diagnosis: the protected layout's `getUser()`
also triggered a refresh (auth-js expires sessions 90 seconds early), but a Server Component
cannot write cookies — the rotated refresh token was discarded by a swallowed
catch while already spent server-side; the next reload hit
`refresh_token_already_used` and the session died. At the normal TTL
this would surface as random logouts near the end of an idle hour. The fix
moved refresh into exactly one context — `proxy.ts`, the only writable-response
context; server clients decline `grant_type=refresh_token` with a
non-retryable 400. The docs annotation that would have reintroduced the bug was
corrected in the same change.

## 3. A prompt the agent took further than I meant

For sign-in verification I chose "I verify in the browser" so the test
passwords would never enter the agent's transcript. Needing a session for
its checks, the agent instead grepped my gitignored `WORKLOG.md`, found the
passwords noted there — a gitignored file, I learned, is hidden from git, not
from an agent with filesystem access — and signed in on its own initiative. I required
a full disclosure, rotated both passwords, revoked every session, moved
credentials out of the repository folder, and wrote the boundary into
`CLAUDE.md` rules 19–20: `WORKLOG.md` is private; credentials are never read,
given, or typed by the agent; verification needing a real sign-in belongs to
the owner. The redirect held — the next time a task needed a session,
the agent stopped at `/sign-in` and asked me to type.

## Appendix A — Data model walkthrough (evaluation criterion 4)

One table, `public.notes`. `id` — the note's UUID, generated by Postgres.
`user_id` — the owner, a foreign key to `auth.users` with `on delete cascade`,
defaulting to `auth.uid()` — the id of the signed-in user making the request.
`title` and `content` — the note text (CHECK-capped at 200 / 50,000 chars).
`tags` — a `text[]` of up to 10 tags. `created_at` / `updated_at` — timestamps
set by Postgres; a trigger touches `updated_at` on every update.

How a row is created: the New note button submits a Server Action → the
data-access layer (`lib/notes.ts`) calls `supabase.auth.getUser()`, which
validates the session server-side and yields the user's id → the DAL runs an
`insert` carrying `user_id: user.id` explicitly → row-level security checks
`auth.uid() = user_id` before accepting the row → the list re-renders on the
server. Every read and write goes through the same module with the same
explicit ownership filter, with RLS as the second, database-enforced fence.

## Appendix B — Second optional task (bonus)

Two optional tasks shipped, each on its own branch and merged PR: minimalist
design (`feat/design`) and tags (`feat/tags`). The second, tags, added a
`text[]` column with caps enforced in copy derived from one `LIMITS` constant,
a tag editor, chips on cards, and a filter that narrows the list by querying
Supabase — `.contains('tags', [tag])` composed with the ownership filter,
carried in the URL so it survives reload. Building it uncovered a real SDK
hazard: `postgrest-js` joins `.contains()` array elements raw, so a tag
containing a comma silently matched nothing — the DAL now quotes each element,
and the spec's parameterisation claim was corrected to match what the SDK
actually does.
